# Lifecycle производственного Delo

Дата проверки: 11 сентября 2026 года.

## Win+D

Проверена настоящая сборка `app/bin/Delo.exe` в отдельной сессии `--harness=lifecycle-20260911`, а не оконный прототип. В harness diagnostics добавлены прямые Win32-показатели `IsWindowVisible`, `IsIconic` и фактический owner HWND.

До Win+D:

```text
healthy=true, errors=0
windowVisible=true, iconic=false
owner=197936, window=1115098
copied=76, rendered=2
```

После физически отправленного Win+D и ожидания 2 секунд:

```text
healthy=true, errors=0
windowVisible=true, iconic=false
owner=197936, window=1115098
copied=128, rendered=2
```

Процесс оставался отвечающим. Окно не было свёрнуто или скрыто, owner рабочего стола не изменился, захват продолжал получать кадры, а renderer не сообщил ошибок. Повторное Win+D вернуло окна пользователя; Delo затем штатно завершился через `beforeExit`/save acknowledgement.

Это закрывает проверенный случай Win+D на текущем основном мониторе и текущем DPI. Смена Explorer, перенос между физическими мониторами и разные DPI остаются отдельными сценариями.

## Покой и ресурсы

Production renderer проверен в сессии `--harness=idle-20260911` после Win+D на неподвижном рабочем столе. За 10 секунд WGC передал 4 кадра, но счётчик отрисовок не изменился: `rendered=92` до и после. Renderer остался `healthy=true`, `errors=0`, окно — видимым и не свёрнутым.

Параллельное измерение за 12 секунд показало 15,62 мс CPU, то есть около 0,13% одного логического ядра. Working Set остался 54,69 МиБ, Private Memory — 65,86 МиБ. Контрольный прогон поверх меняющегося окна Codex дал новые presents, что является требуемой реакцией стекла на изменение захваченного фона, а не собственной декоративной анимацией.

## Сон и блокировка

Host принимает `PBT_APMSUSPEND`, `PBT_APMRESUMEAUTOMATIC`, `WTS_SESSION_LOCK` и `WTS_SESSION_UNLOCK`. Перед паузой он рассылает domain-команду `suspend` и сбрасывает WGC/D3D resources; после возобновления создаёт их заново. Таймер использует `QueryUnbiasedInterruptTimePrecise`, поэтому время сна не должно попадать в рабочий интервал.

Первый реальный прогон production app в сессии `sleep-production-20260911` воспроизвёл исчезновение виджета после пробуждения. Windows Event Log зафиксировал native crash `0xc0000005` в `Delo.exe`, RVA `0x21BCE`. Дизассемблирование сопоставило адрес с разыменованием GPU внутри `GlassRenderer::Tick`. WGC/DComp-вызов может вложенно обработать power/display message; прежний `Reset()` в этот момент освобождал GPU и capture прямо посреди текущего Tick. Данные не повредились: задача была сохранена как paused.

Исправление добавляет защиту от повторного Tick и откладывает `Rebuild`/`Suspend` reset до выхода из текущего Tick. После сборки повторный реальный сон выполнен в сессии `sleep-production-fix-20260911` с работающим таймером. До сна: `healthy=true`, `errors=0`, `recoveries=1`, elapsed 1492,75 мс. После пробуждения:

```text
powerSuspends=3, powerResumes=3
healthy=true, errors=0, recoveries=4
windowVisible=true, iconic=false
workState=paused, elapsedMs=24822.46
```

Несколько power-событий ожидаемы: Windows прислал session lock/unlock и системные suspend/resume уведомления. Таймер исключил период сна при сравнении с wall-clock. Все 6 post-resume проверок прошли; процесс продолжал отвечать, новых Application Error/WER событий для Delo после исправления нет. После штатного выхода и повторного запуска той же сессии прошли ещё 4 проверки: задача и elapsed сохранились, состояние осталось paused, renderer снова healthy/errors=0.

## Этап A на 0.1.10, 26 сентября

Проверки первой версии на текущей сборке (SPEC, раздел 12). Набор: `app/tests/run-lifecycle.ps1` держит одну harness-сессию с идущим таймером через реальные события, `app/tests/lifecycle-check.mjs` после каждого события снимает состояние harness-виджета и рабочего виджета пользователя (установленная 0.1.10), `app/tests/lifecycle-native.ps1` читает положение окна, монитор, DPI и записи Windows о сбоях и сне. Холостой прогон без события — 12/12.

**Сон (V13) — PASS 14/14.** Ноутбук ASUS TUF A16 работает в Modern Standby (S0 low power idle). Windows записала вход в сон 20:13:43 и выход 20:14:49; harness и рабочий виджет получили suspend и resume, стекло восстановлено без ошибок, окна видимы, таймер на паузе, после перезапуска harness пауза и 1742 с сохранены, сбоев Delo нет. Уточнение к П3: в Modern Standby `QueryUnbiasedInterruptTimePrecise` не останавливается во сне (за 1832 с настенного времени он прибавил 1831 с), поэтому время сна исключает не часы, а пауза таймера по сигналу suspend. Критерий проверки переписан на записи Kernel-Power 506/507.

**Масштаб (V10, N03) — дефект найден и исправлен.** На 0.1.10 при 150 %, 200 %, 100 % и возврате к 125 % таймер, данные, отклик, ввод и рабочий виджет в порядке, но:

- Windows не присылала окнам `WM_DPICHANGED`: `GetDpiForWindow` рабочего виджета оставался 120 при мониторе 192, harness — 144. Окно сохраняло физический размер, при 200 % виджет сжимался до 263×388 DIP (ниже минимума 320×360), при 100 % становился крупнее. Стекло брало масштаб из того же устаревшего DPI.
- На 100 % стекло один раз выдало ошибку и восстановилось само; ошибки стекла не писались в журнал, причина не установлена.

Исправление (`native/Dpi.h`, `Host.cpp`, `GlassRenderer.cpp`): масштаб берётся у монитора окна (`GetDpiForMonitor`); окно сверяет его на `WM_DPICHANGED`, `WM_DISPLAYCHANGE`, `WM_SETTINGCHANGE` и раз в 2 с и пересчитывает размер по выбранному пользователем размеру в DIP с привязкой к левому верхнему углу и ограничением рабочей областью; выбранный размер переживает это ограничение и меняется только изменением размера, не перемещением; сохранённые границы хранят масштаб и размер в DIP; стекло считает скругления по масштабу монитора; `dpi_changed` и `glass_error` пишутся в журнал. Проверено на реальной смене масштаба: 125 → 200 % — окно 840×1104 физ. (420 DIP в ширину, по высоте ограничено экраном), 12/12; программное перемещение при 200 % не изменило выбранный размер; 200 → 125 % — окно снова 420×620 DIP, 12/12; запуск сразу при 200 % — 8/8. Все смены пойманы опросом (`poll`) за 1 с.

**Перезапуск Explorer (V02) — PASS 12/12.** С разрешения пользователя Explorer завершён и сам поднят Windows (новый процесс через ~1 с). Harness (исправленная сборка) и рабочий виджет (0.1.10), оба откреплённые, остались видимы и заново привязаны к новому Progman; стекло без ошибок, таймер шёл без потерь, данные на месте; значки в трее у обоих восстановлены (`Shell_NotifyIconGetRect` находит их).

**Второй рабочий стол Windows — PASS 12/12.** После переключения на второй виртуальный рабочий стол пользователь видит оба виджета; Windows не скрывает ни одно окно для этого стола (DWMWA_CLOAKED = 0), таймер шёл, стекло без ошибок.

Второго монитора у пользователя нет.

**Чистая Windows (V12) — PASS, 27 сентября.** Windows Sandbox: Windows 11 Корпоративная 10.0.26100 без инструментов разработки, каждый прогон в новой песочнице. Команда `app/tests/run-windows-sandbox.ps1 -From 0.1.10` сама поднимает песочницу через `wsb start`/`wsb connect`, выполняет `sandbox-guest.ps1` и останавливает её. Сценарий обновления: установлена опубликованная 0.1.10; её рабочий виджет запущен на данных с задачей и загрузился; поверх работающего виджета тихо установлена 0.1.11 — установщик закрыл 0.1.10 через `Delo.RequestExit`, поставил 0.1.11 (48 файлов, ProductVersion 0.1.11) и снова запустил виджет, около 41 с; задача на месте. Затем harness 0.1.11 на этих данных: старая задача видна, через интерфейс создана новая, стекло healthy без ошибок; после перезапуска обе задачи сохранены. Удаление закрыло запущенный виджет, убрало `Delo.exe` и не тронуло данные. Прогон повторён трижды, все PASS; отдельно чистая установка 0.1.11 без старой версии — PASS. Ограничения: в образе песочницы WebView2 Runtime уже установлен, поэтому ветка установки runtime и ошибка установщика 267 здесь не проверяются; рабочий виджет 0.1.10 проверяется по журналу и файлу данных, потому что его DevTools в песочнице не открываются (см. ниже).

Попутно найдено: Windows Sandbox игнорирует `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` и ключ политики `AdditionalBrowserArguments`, поэтому harness до 0.1.11 не открывал там DevTools. Начиная с 0.1.11 порт передаётся через `ICoreWebView2EnvironmentOptions::put_AdditionalBrowserArguments`; на рабочей машине harness работает как прежде. Запуск `WindowsSandbox.exe` с `.wsb` из неинтерактивной оболочки на этой машине по-прежнему падает (`WindowsSandboxRemoteSession` не загружает `hostfxr.dll`), а `wsb start` + `wsb connect` работают.
