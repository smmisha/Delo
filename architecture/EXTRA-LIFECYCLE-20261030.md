## Физический цикл питания

После разрешения пользователя на основном ноутбуке запущена отдельная копия runtime с именованным harness-профилем и одной синтетической задачей. Пользовательская база не использовалась; проверка обычной установленной копии в этот сценарий не входит.

Исходное состояние — 7/7 PASS: окно видимо, стекло исправно, размеры HWND/WebView/material совпадают, нет переполнения, масштаб 125%, хост отвечает. Затем вызван штатный запрос сна Windows; пользователь разбудил и разблокировал ноутбук.

Фактический цикл зафиксирован событием `Microsoft-Windows-Power-Troubleshooter`, ID 1: `SleepTime=2026-10-30T00:04:41.5541342Z`, `WakeTime=2026-10-30T00:15:41.9047160Z`, длительность 660350,58 мс. `TargetState=5`, `EffectiveState=5` соответствуют гибернации S4 по [SYSTEM_POWER_STATE](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ne-winnt-system_power_state). Этот цикл не объявляется длительным испытанием Modern Standby S0.

После пробуждения — 15/15 PASS: suspend/resume получены, окно видно, renderer healthy/errors=0, recoveries 1 → 3, задача не потеряна, таймер остался paused. Сохранённое время задачи — 50347,37 мс; подтверждены исключение записанного интервала сна и остановка таймера не позднее входа в сон с допуском 3 с. Application Error/WER/Hang для Delo за проверенный период не обнаружены.

После штатного сохранённого выхода и повторного запуска того же профиля — 5/5 PASS: задача и пауза сохранены, `elapsedMs` точно совпал с результатом после пробуждения, renderer исправен, размеры материала и окна совпадают.

### Исправление диагностического измерения

Первая частная проверка длительности дала 12/14: она неверно использовала `TimeCreated` ближайших Kernel-Power 506/507, отражавших короткий переход после возобновления. Реальную продолжительность подтверждают поля `SleepTime/WakeTime` события Power-Troubleshooter, а не время публикации тех событий. Сбор данных исправлен только в локальном диагностическом скрипте, с проверкой принадлежности цикла периоду текущего baseline. Добавлены проверки минимальных 10 с реального энергосбережения, исключения его длительности и остановки таймера ко входу в сон. Итоговые 15/15 проверяют тот же физический цикл; повторный сон для них не выполнялся. Исходный FAIL сохранён, код приложения не исправлялся ради этого результата.

Доказательства: `physical-results/baseline.json`, `after-sleep.json` (первый FAIL), `after-sleep-fields.json`, `relaunch.json`, `sleep-request.json`, `sleep-return.json`, `power-events.xml`, частные `lifecycle-check.mjs`/`lifecycle-native.ps1` в игнорируемом `app/test-output/extra-audit-20261030/`. Системные XML и снимки рабочего стола не публикуются.

## Что осталось непроверенным

- Смена масштаба 125% → 200% → 125% на этой сборке: исходные 125% проверены, затем пользователь отложил смену. Настройки экрана не менялись. Два доступных канала управления Windows UI завершались таймаутом; замена настройки через реестр не выполнялась.
- Перенос между реальными мониторами и подключение/отключение второго экрана: во время проверки активен один монитор.
- Отдельный длительный цикл Modern Standby S0: текущий физический цикл был S4.
- Установка на чистой Windows без WebView2: стандартная Sandbox содержит runtime и не закрывает эту ветку установки.

После отказа от смены масштаба тестовая копия штатно закрыта, работающего host harness и Sandbox не осталось. Успех выполненных групп не повышает статусы перечисленных непроверенных сценариев.
