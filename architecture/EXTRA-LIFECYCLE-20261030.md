## Физический цикл питания

После разрешения пользователя на основном ноутбуке запущена отдельная копия runtime с именованным harness-профилем и одной синтетической задачей. Пользовательская база не использовалась; проверка обычной установленной копии в этот сценарий не входит.

Исходное состояние — 7/7 PASS: окно видимо, стекло исправно, размеры HWND/WebView/material совпадают, нет переполнения, масштаб 125%, хост отвечает. Затем вызван штатный запрос сна Windows; пользователь разбудил и разблокировал ноутбук.

Фактический цикл зафиксирован событием `Microsoft-Windows-Power-Troubleshooter`, ID 1: `SleepTime=2026-10-30T00:04:41.5541342Z`, `WakeTime=2026-10-30T00:15:41.9047160Z`, длительность 660350,58 мс. `TargetState=5`, `EffectiveState=5` соответствуют гибернации S4 по [SYSTEM_POWER_STATE](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ne-winnt-system_power_state). Этот цикл не объявляется длительным испытанием Modern Standby S0.

После пробуждения — 15/15 PASS: suspend/resume получены, окно видно, renderer healthy/errors=0, recoveries 1 → 3, задача не потеряна, таймер остался paused. Сохранённое время задачи — 50347,37 мс; подтверждены исключение записанного интервала сна и остановка таймера не позднее входа в сон с допуском 3 с. Application Error/WER/Hang для Delo за проверенный период не обнаружены.

После штатного сохранённого выхода и повторного запуска того же профиля — 5/5 PASS: задача и пауза сохранены, `elapsedMs` точно совпал с результатом после пробуждения, renderer исправен, размеры материала и окна совпадают.

### Исправление диагностического измерения

Первая частная проверка длительности дала 12/14: она неверно использовала `TimeCreated` ближайших Kernel-Power 506/507, отражавших короткий переход после возобновления. Реальную продолжительность подтверждают поля `SleepTime/WakeTime` события Power-Troubleshooter, а не время публикации тех событий. Сбор данных исправлен только в локальном диагностическом скрипте, с проверкой принадлежности цикла периоду текущего baseline. Добавлены проверки минимальных 10 с реального энергосбережения, исключения его длительности и остановки таймера ко входу в сон. Итоговые 15/15 проверяют тот же физический цикл; повторный сон для них не выполнялся. Исходный FAIL сохранён, код приложения не исправлялся ради этого результата.

Доказательства: `physical-results/baseline.json`, `after-sleep.json` (первый FAIL), `after-sleep-fields.json`, `relaunch.json`, `sleep-request.json`, `sleep-return.json`, `power-events.xml`, частные `lifecycle-check.mjs`/`lifecycle-native.ps1` в игнорируемом `app/test-output/extra-audit-20261030/`. [Microsoft описывает выключение экрана как точку входа в Modern Standby](https://learn.microsoft.com/en-us/windows-hardware/design/device-experiences/prepare-software-for-modern-standby).

Kernel-Power 506/507 подтвердили сессию от 03:15:18,865 до 03:18:51,853 (Europe/Kiev): `DurationInUs=212990038`, `SleepEntered=true`, `SleepDurationInUs=207017973`, `DripsResidencyInUs=173499245`. Таким образом, внутри сессии около 213 с зафиксированы около 207 с сна и 173 с DRIPS. Связанной гибернации S4 в проверенном интервале нет.

После пробуждения 16/16 PASS: окно и размеры восстановлены, стекло healthy/errors=0, suspend/resume получены, задача сохранена, таймер остался paused; фактическое время S0 исключено, остановка таймера произошла не позднее входа в сон с допуском 3 с. Новых Application Error/WER/Hang для Delo за проверенный период не обнаружено.

Начальный замер после ручного сообщения о пробуждении дал 10/16: после его baseline новых power-событий не было, поэтому он не доказывал переход сна. Частный сборщик адаптирован: пары проверяются по BootId, ScenarioInstanceIdV2 (при его наличии), порядку времени и совпадению длительности с допуском 2 с. Итоговые 16/16 повторно оценивают тот же физический цикл; первоначальные результаты сохранены. Код приложения и штатные тесты не менялись.

## Попытка проверки установки без WebView2

В одноразовой Sandbox проверен опубликованный installer Delo 0.3.9 с SHA-256 `3FE6E1A90761B787A0F706F44B462C9DEE92A685AB4E62821EE3A329FBC33A7A`. Отсутствие зависимости требовалось подтвердить двумя независимыми признаками: ошибка `GetAvailableCoreWebView2BrowserVersionString` из SDK и отсутствие регистраций runtime. Пустой ответ пробника не принимался за отсутствие runtime в окончательном сценарии.

SDK и регистрация подтвердили установленный WebView2 `156.0.4314.50`. Документированная [команда штатного удаления Microsoft](https://techcommunity.microsoft.com/blog/intunecustomersuccess/support-tip-bulk-installing-webview2-runtime-on-windows-10-devices/3678202) вернула код 93; SDK и регистрация продолжали показывать тот же runtime. Повтор из гостевого контекста SYSTEM также вернул 93. Поэтому ветка «runtime отсутствует → bootstrap устанавливает его» осталась непроверенной в доступном образе. Подмена реестра или файлов для получения ложного отсутствия не выполнялась; основной компьютер для удаления зависимости не использовался.

Обычная установка при уже имеющемся runtime прошла в первом подпрогоне: installer exit=0, задача создана и пережила relaunch, удаление exit=0, данные сохранены. Это не закрывает ветку отсутствующей зависимости. Первые диагностические попытки имели ошибки временного пробника (экранирование пути C# и получение ExitCode дочернего процесса в PowerShell 5.1); они сохранены как неуспешные. Исправленный пробник и supervisor отдельно проверены локально до окончательных попыток удаления.

Доказательства: игнорируемый `app/test-output/dependency-audit-20261030/`; последние независимые попытки — `sandbox-20261030-030944-20d04e` и `sandbox-20261030-031209-fdc020`, с SDK-результатами, кодами удаления и итоговыми `passed=false`. Собственные Sandbox остановлены после каждого запуска. Эти результаты показывают ограничение доступной проверки, а не установленную ошибку installer Delo.

## Недоступные условия

- Второго монитора у пользователя нет. Перенос и подключение/отключение реального второго экрана исключены пользователем из текущего набора приёмки и не объявляются PASS.
- Ветка установки без WebView2 требует другого чистого образа Windows: доступная Sandbox сохранила runtime после двух штатных попыток удаления в разных контекстах.

После каждого этапа тестовая копия штатно закрыта, работающего host harness и Sandbox не осталось. Успех выполненных групп не повышает статусы перечисленных непроверенных сценариев.
