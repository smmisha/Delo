# Renderer: отзывчивость и приостановка захвата

Проверка 2 октября 2026 года. Первый прогон ниже относится к исходникам и отдельной тестовой сборке. В последующем ночном прогоне собран Store-пакет 0.3.2; его результаты приведены отдельно. Публичный Inno-установщик не пересобирался.

## Подтверждённые изменения

В `app/native/GlassRenderer.cpp` прежний детектор изменения crop повторно ожидал готовность D3D11 query на UI-потоке, с общим дедлайном 50 мс. Теперь он отправляет один query, выполняет один `Flush` и проверяет результат не более одного раза за вызов. `S_FALSE` возвращает управление без ожидания. Не завершившийся за 10 секунд query вызывает восстановление renderer с фазой `change_query` в ошибке.

Версии исходного crop и query позволяют проверить последний изменившийся crop, даже если после него больше не приходит WGC-кадров. Эталон обновляется после успешного `Present`. Принудительная отрисовка после смены темы и перемещения отменяет старый pending query; resize ждёт заполнения новой текстуры. Одновременно допускается один pending query. Это не является общим ограничением очереди всех GPU-команд или количества monitor-copy операций.

В `app/native/Host.cpp` системный сон и блокировка сеанса теперь имеют независимые признаки в `CaptureSuspension.h`. Автоматическое пробуждение не снимает оставшуюся блокировку сеанса. UI получает suspend/resume по переходу суммарного power-состояния. Demo-mode отдельно блокирует renderer; откат режима и создание нового renderer учитывают все текущие причины приостановки.

В ошибках renderer сохранён HRESULT и добавлена фаза: build, resize, device, first_frame, capture_exclusion, capture, change_query, draw или present. Исторический HRESULT `0x80070102` сам по себе не позволяет установить, на каком этапе возникли прежние таймауты.

Живой harness проверил отвечающий WebView, заполненный материал основного окна, обе принудительные темы, исключение основного и быстрого окон из захвата, demo suspend/rebuild, быстрое окно и hide/show. Во всех его renderer-снимках `errors=0`; после demo renderer восстановился с `recoveries` от 1 до 2. Это проверка состояния и отрисовок, а не новый визуальный аудит шейдера.

Первые две попытки живого теста не прошли проверки сценария: первая ожидала новую отрисовку без нормализации исходной темы, вторая ограничивала готовность UI двумя секундами. Затем сценарий получил явную светлую исходную тему и ожидание готовности до шести секунд. Неудачные попытки сохранены отдельно, финальный прогон выполнен после этих исправлений.

Полный wrapper финального запуска занял около 6,4 секунды. Предусмотрены общий watchdog 25 секунд, остановка при свободной RAM ниже 1,25 ГБ или двух последовательных измерениях CPU от 80%. Пять измерений общей нагрузки хоста дали максимум CPU 42% и минимум свободной RAM 1,75 ГБ. Это значения всего ноутбука, не нагрузка одного Delo и не доказательство причины прежних зависаний.

Приложение вышло через собственный bridge без принудительного завершения. Дочерние тестовые процессы завершились. Повторная итоговая проверка: Delo, VMware, vmrun, cl и link отсутствуют; порт 9223 не слушается; CPU 7%, свободная RAM 2,02 ГБ. Эти показатели относятся к моменту проверки.

Доказательства находятся в игнорируемом `app/test-output/renderer-lifecycle-fix/`: `live-result.json`, `load-result.json`, `first-attempt-*`, `second-attempt-*`, сценарии и отдельная сборка `build/Delo.exe`. Они не включают пользовательские задачи: harness использовал свой профиль в каталоге сборки. GPU и pure unit binaries также находятся в игнорируемом test-output.

## Практические ограничения

- Точная причина зависания всей основной машины не установлена. Прежнее улучшение после закрытия VM и локального Delo было наблюдением, а не изолированным доказательством причины.
- Первый короткий Win11-прогон не включал настоящий сон и голосовой runtime. Последующая Win10-проверка ниже закрывает восстановление того же процесса и распознавание подготовленного файла; новую запись микрофона она не проверяет.
- Длительная работа, физическая смена мониторов/DPI, настоящий сбой GPU-драйвера и первоначальный запуск уже заблокированного сеанса без LOCK-уведомления не проверены.

## Документация API

Для реализации использованы первичные источники: [ID3D11DeviceContext::GetData](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-getdata) и [D3D11_ASYNC_GETDATA_FLAG](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ne-d3d11-d3d11_async_getdata_flag). Отсутствующий `Present` при неизменившемся crop требует отдельной отправки query-команд; последующее чтение использует `D3D11_ASYNC_GETDATA_DONOTFLUSH`.
